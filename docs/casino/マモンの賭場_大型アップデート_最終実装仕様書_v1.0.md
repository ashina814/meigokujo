## 0. このアップデートの目的

マモンの賭場を、試験状態の旧制度から正式開業可能な状態へ作り直す。

達成すべき状態は次のとおり。

1. 利用者は **Landだけ**を見て、そのまま遊べる。
2. 両替、変動レート、エテル、退場時奉納を利用者が理解する必要がない。
3. 資金移動はすべて追跡可能で、二重実行・再起動・同時実行でも増減が壊れない。
4. 胴元は、支払えない最大配当を受け付けない。
5. `/賭場` から一回の操作で最初のゲームを開始できる。
6. 開業初日から利用状況と経済状態を計測できる。

今回の更新規模は小さく抑えない。既存の安全な基盤は維持する一方、表示層・チップ層・監査・復旧は完成形に合わせて大きく変更してよい。

### 1.1 通貨

- 利用者向け通貨は **Landのみ**。
- 内部では賭場専用チップを使用する。
- **1チップ = 1 Land** 固定。
- 手動両替を廃止する。
- 変動為替を廃止する。
- 退場時二割奉納を廃止する。
- 利用者向け画面から「エテル」「◈」「レート」「両替」「奉納」を除去する。
- 既存のLand台帳を、ゲーム内の細かな送金で直接汚さない。

### 1.2 旧データ

- 旧賭場は正式運用前の試験状態として扱う。
- 旧エテル、株、VIP、戦績、板などは、原則として新制度へ移行しない。
- 読み取り専用preflightで、保護すべき正式資産がないことを確認したうえで初期化する。
- 正式な権利が見つかった場合は、旧制度全体を移行せず、対象者のみ個別補償する。
- 利用者の通常Land残高と、賭場外データには触れない。

### 1.3 株

- 開業時は停止する。
- コマンド登録とホーム導線から外す。
- 試験データであることを確認できた建玉は初期化する。
- 正式保有が確認された場合は、運営決裁後に個別補償する。
- 将来は、既存の板機構を利用した短期予想ゲームへの再設計を第一候補とする。

### 1.4 対人卓（廃止）

**永続対人順位卓は実装しない（2026-08-16 廃止）。** 詳細は §13 を参照。
ボット外のゲーム結果を賭場が仲介する機能は持たない。同種の賭けは `/板` を使う。

### 1.5 チンチロ

- 現行の敗北倍率最大5倍は初心者向けUIと整合しないため、**敗北倍率を最大2倍へ変更する**。
- PR4で現行RTPを測定し、敗北倍率変更後も基準RTPとの差を±0.5ポイント以内に収めるよう、勝利側倍率を最小限調整する。
- 調整後の倍率表とRTPはPR4のレビュー資料に明記する。
- ゲーム開始時に最大損失 `2 × bet` を預託する。
- 結果後の追加徴収や、残高不足による通常負けへのフォールバックは行わない。

## 3. 必ず守る不変条件

### I1. 準備金完全一致

```text
全チップholderの残高合計
= ledger.balanceOf("sys:escrow:casino")
```

1 Ldの差も許容しない。崩れた場合は賭場を自動停止し、不整合のまま返還・精算を行わない。

### I2. 内部送金の総量保存

```text
internal_transferでは、全チップ残高の合計が変化しない。
```

### I3. 預入・返還のLand連動

```text
預入:  準備Land +X / 発行チップ +X
返還:  準備Land -X / 発行チップ -X
```

預入・返還には、対応するLand台帳取引IDを必須で保存する。

### I4. 追記記録

チップ移動は、開始残高を除き、すべて `casino_tx` に追記する。理由不明の取引を作らない。

### I5. 金銭処理の冪等性

外部から呼ばれる金銭操作は、最上位で必ず `runChipGroup()` を一度だけ通す。プロセス内ロックだけで金銭の冪等性を担保しない。

### I6. 不明時は動かさない

所有元、帳簿、実残高、状態のいずれかが一致しない場合、自動返金・自動精算をしない。対象だけを凍結し、人間へ通知する。

### I7. 胴元残高を負にしない

ゲーム開始前に最大債務を予約する。予約できないゲームは開始しない。

### I8. 表示と利用可能額の整合

- `所持` = 通常Land + 自由チップ
- `預け中` = 卓・板に拘束されている本人帰属額
- 預け中資金を利用可能額に含めない。

### I9. 補助運営ロールは金銭を操作しない

接客・進行・開催補助などを目的とする**非管理ロール**へ、返金・残高調整・配当・house投入・
強制精算といった金銭操作APIを付与しない。

資金操作権限を新たに足す場合は、役職の追加とは**独立した金融権限**として明示的に設計し、
レビューを通すこと。「その役職の仕事に必要だから」を理由に金銭APIを抱き合わせない。

（この不変条件の元になった賭博場従業員は 2026-08-16 に廃止済み。ルールは一般形で残す。）

### I10. 資金裁定と人物処分を分離

賭場は資金と戦績のみを決める。参加停止日数、罰金、ロール処分等は運営または冥府裁判所が決める。

## 5. 取引ログと冪等性

### 5.1 `casino_tx_groups`

```sql
CREATE TABLE casino_tx_groups (
  group_key    TEXT PRIMARY KEY,
  kind         TEXT NOT NULL,
  status       TEXT NOT NULL,
  actor_id     TEXT NOT NULL,
  result_json  TEXT,
  created_at   INTEGER NOT NULL,
  settled_at   INTEGER
);
```

`kind`例:

- `solo_game`
- `table_hold`
- `table_start`
- `table_settle`
- `table_refund`
- `market_settle`
- `deposit`
- `redeem`
- `daily`
- `vip`
- `shop`
- `opening_reset`

`status`:

- `settled`
- `failed`

技術例外はDBトランザクションごとロールバックし、行を残さない。

### 5.2 `casino_tx`

```sql
CREATE TABLE casino_tx (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  group_key       TEXT NOT NULL,
  seq             INTEGER NOT NULL,
  tx_kind         TEXT NOT NULL,
  from_holder     TEXT,
  to_holder       TEXT,
  amount          INTEGER NOT NULL CHECK(amount > 0),
  reason          TEXT NOT NULL CHECK(length(trim(reason)) > 0),
  game            TEXT,
  session_id      TEXT,
  actor_id        TEXT NOT NULL,
  ledger_tx_id    INTEGER,
  created_at      INTEGER NOT NULL,
  FOREIGN KEY(group_key) REFERENCES casino_tx_groups(group_key)
);
```

`tx_kind`:

| 種別 | from | to | `ledger_tx_id` |
|---|---|---|---|
| `internal_transfer` | 必須 | 必須 | NULL |
| `deposit` | NULL | 必須 | 必須 |
| `redeem` | 必須 | NULL | 必須 |

### 5.3 開始残高

```sql
CREATE TABLE casino_chip_opening_balances (
  opening_version TEXT NOT NULL,
  holder          TEXT NOT NULL,
  amount          INTEGER NOT NULL CHECK(amount >= 0),
  created_at      INTEGER NOT NULL,
  PRIMARY KEY (opening_version, holder)
);
```

検算:

```text
開始残高
+ internal_transfer受取 - internal_transfer支払
+ deposit - redeem
= 現在残高
```

### 5.4 PR1導入時の旧残高

PR1導入時に、既存 `ether_balances` を一度だけ次の版として保存する。

```text
opening_version = legacy_pre_reset
```

正式開業初期化時に、現行版を次へ切り替える。

```text
opening_version = opening_v1
```

### 5.5 `runChipGroup()`

一つの業務操作を単一DBトランザクションで処理する。

```text
1. group_keyをINSERTして処理権を取得
2. 既存ならresult_jsonを返し、資金を動かさない
3. 必要な送金・状態変更を実行
4. result_jsonとsettled_atを保存
5. COMMIT
```

対象:

- ソロゲーム精算
- PvP精算
- エスクロー預託・返金・精算
- 板の参加・返金・精算
- 福分け
- VIP
- 商店購入
- 株売買（停止前の互換経路）
- チップ預入・返還
- 一時対人ゲームの開始・精算・返金

`casino_tx`の行があるのに、対応する`casino_tx_groups`がない状態を許さない。

## 6. 検算

### 検算A: 取引履歴と残高

holderごとに、開始残高と全取引から現在残高を再現する。

### 検算B: 準備金

```text
Σ casino_chips = sys:escrow:casino のLand残高
```

### 検算C: エスクロー

```text
参加者別預託帳簿合計 = escrow holder実残高
```

### 検算D: 系全体

利用者総資産、house、JP、relief、quarantineとLand準備口座の全体整合を独立に確認する。

### 実行時期

- Bot起動時
- 開業初期化時
- 支配人の手動検算
- 日次バッチ
- 重大な資金操作後

A〜DのいずれかがNGなら `integrity_halt` にする。

## 8. 起動・復旧

### 8.1 登録型復旧

```ts
recoveryRegistry.register({
  type: "market",
  listLiveEscrowHolders: ...,
});
```

一時対人ゲーム・ルーレット・競馬はコレクタのみで永続状態がないため登録しない。
再起動時は孤児として返金する。

### 8.2 `recoverCasino()`

```text
S1  startup_checkへ移行
S2  Land台帳検算
S3  チップ検算A・B
S4  recoveryRegistryから生存中エスクローを収集
S5  帳簿とholder残高を照合
S6  生存中かつ一致する預託は維持
S7  所有元が確実に存在しない孤児だけ返金
S8  帳簿なし残高はquarantineへ隔離
S9  ソロゲームの債務予約を解放
S10 自由チップだけLandへ返還
S12 問題がなければ、元の状態がstartup_checkの場合だけopenへ戻す
```

S11（永続卓のメッセージ復旧）は対人順位卓の廃止で対象が無くなったため存在しない。
番号は監査記録との対応を保つためそのままにしてある。

### 8.3 例外

- S2・S3 NG: `integrity_halt`。以降を実行しない。
- 帳簿不一致: 対象だけ凍結。返金しない。
- 一件の孤児返金失敗: 他の復旧を止めない。

## 9. 自動預入・返還

### 9.1 預入

- 賭け直前に自由チップが不足している場合だけ実行。
- 不足分ちょうどを預ける。
- 切り上げ・まとめ預入をしない。
- 本人が指定していない額を勝手に動かさない。
- Land不足ならチップを発行しない。
- Land取引とチップ発行を同一SQLiteトランザクションで行う。

### 9.2 返還

自由チップだけを全額返還する。

契機:

1. `[賭場を出る]`
2. 賭場操作から10分無操作
3. Bot起動時
4. 支配人による緊急返還
5. 賭場外操作で利用者が明示的に返還を承認した時

卓・板に預託中の資金は返還しない。

### 9.3 賭場外のLand不足

自動では返還しない。

```text
Landが足りません。
賭場に1,000 Ldあります。

[Landへ戻して続ける] [やめる]
```

押された場合だけ返還し、元の操作を冪等に一度だけ再実行する。進行中のソロゲームまたは対人卓がある場合は、このボタンを出さない。

## 10. 正式開業初期化

### 10.1 開業設定

未設定判定に0を使わない。NULLまたは明示的な設定完了フラグを使う。

```text
casino_opening_capital
casino_opening_house
casino_opening_jackpot
casino_opening_relief
casino_min_working_capital
casino_remit_rate_bps
casino_opening_configured
```

制約:

```text
opening_capital > 0
opening_house > 0
opening_jackpot >= 0
opening_relief >= 0
opening_house + opening_jackpot + opening_relief = opening_capital
opening_configured = true
```

### 10.2 読み取り専用preflight

すべてSELECTのみ。

確認:

- 利用者がLandを払ってエテルを買った正味実績
- 有効VIP
- 正式な株保有
- 保全対象と判断すべき戦績
- 旧準備口座のLandの出所
- quarantineにある利用者帰属資産

一件でも該当すれば初期化を止め、対象者別の補償一覧を運営へ出す。

### 10.3 補償

- 基準は、現在の正当な保有価値をLandへ換算する時価ベースを原則とする。
- 原資は `sys:dept:賭博場`。
- 原資不足なら開業初期化を中止する。
- 不足額をquarantine上の架空残高として処理しない。
- 全件補償完了後、preflightを再実行する。

### 10.4 初期化手順

```text
R0  maintenance / opening_resetで停止
R1  DBスナップショット、SHA-256、旧賭場CSVを保存
R2  読み取り専用preflight
R3  旧Discord一時VCを削除し、完了を確認
R4  BEGIN
R5  進行中エスクロー・板が0であることを確認
R6  旧賭場専用データを初期化
R7  旧準備口座 → 賭博場部署へ「旧制度清算」
R8  賭博場部署 → 新準備口座へ「新制度出資」
R9  casino_chips / casino_tx / groups / reservationsを初期化
R10 opening_v1の開始残高をhouse・jackpot・reliefへ設定
R11 新設定を有効化
R12 同じDBトランザクション内で検算V1〜V7
R13 全件OKならCOMMIT。NGならROLLBACK
R14 openへ変更し、監査チャンネルへ開業記録
```

R7とR8は必ず別のLand取引にする。

```text
sys:escrow:ether → sys:dept:賭博場  旧制度清算
sys:dept:賭博場 → sys:escrow:casino 新制度出資
```

利用者通常Landと賭場外データの変更件数が0であることを検証する。

## 11. 胴元債務予約

### 11.1 モデル

```ts
interface GameLiabilityModel {
  game: string;
  maxHouseLiability(ctx): number;
  maxPlayerLoss(ctx): number;
  maxBetFor(available, ctx): number;
}
```

倍率・役判定はcoreのゲームモデルを真実源とし、予約コードへ写さない。

### 11.2 予約

```sql
CREATE TABLE casino_house_reservations (
  key        TEXT PRIMARY KEY,
  amount     INTEGER NOT NULL CHECK(amount > 0),
  game       TEXT NOT NULL,
  user_id    TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
```

- `house.available = house.balance - reserved`
- 予約とavailable再確認を同一トランザクションで行う。
- 精算・中止・例外時に解放する。
- Bot起動時にソロ予約を全解放し、件数・総額を記録する。

### 11.3 `effectiveMaxBet`

表示時:

```text
min(
  設定上限（VIPなら×2）, 
  gameModel.maxBetFor(house.available, context)
)
```

実行時に再検証する。別利用者の予約によるTOCTOU失敗時は、現在押せる金額を提示して戻す。

### 11.4 チンチロ

- `maxPlayerLoss = 2 × bet`
- 開始時に最大損失を `escrow:session:<sid>` へ預託。
- 通常負けなら必要額だけhouseへ、残り返却。
- 2倍負けなら全額houseへ。
- 勝ち・引き分けなら預託全額返却。
- PR4でRTPを再測定し、現行基準との差を±0.5ポイント以内に調整する。

### 11.5 ホールデム

1. 最大コール経路を安全側に算出できれば採用。
2. 難しければホールデムだけ上限を厳しくする。
3. 安全を証明できなければホールデムだけ停止する。

賭場全体を止めない。

## 15. 安全上限

### 15.1 同時参加・露出上限

- ルーレット・一時対人ゲーム・競馬など、**露出枠を確保する共有セッション**では、
  そのセッションでの最大損失が所持額の50%を超える参加はできない。
  （ソロゲームは日次損失枠だけを見る。所持50%判定は露出型の経路が持つ。）
- ソロゲーム・ルーレット・一時対人ゲーム・競馬は相互に排他とし、
  同時に参加できる賭博セッションは1つまで。

### 15.2 日次純損失上限

初期値は、当日の開始時点所持Landの30%。設定で変更可能。

含める:

- ソロゲームの実現純損失
- ルーレット・一時対人ゲーム・競馬など、露出枠を使うゲームの実現純損失

含めない:

- VIP
- 商店購入
- 通常の送金

利用者が自分で、より厳しい固定額または割合を設定できる機能は開業後の追加候補。
